## 1. Цель исследования

Изучить международные и российские стандарты, применяемые при создании программного обеспечения, классифицировать их и продемонстрировать совместное применение при проектировании, реализации, тестировании и сопровождении CafeteriaPOS.

## 2. Классификация стандартов

| Стандарт | Категория | Назначение | Применение в CafeteriaPOS |
|---|---|---|---|
| ISO/IEC/IEEE 12207:2026 | Процессы | Жизненный цикл программного обеспечения | Планирование разработки, реализация, тестирование и сопровождение |
| ISO/IEC 25010:2023 | Качество продукта | Модель качества программного продукта | Анализ сопровождаемости и функциональной корректности |
| ГОСТ Р ИСО/МЭК 25010-2015 | Качество продукта | Российская модель качества систем и ПО | Оценка качества учебного приложения |
| IEEE 1012-2024 | Верификация и валидация | Организация проверки программных систем | Проверка поведения API и анализ результатов тестирования |
| ГОСТ 19.201-78 | Документация | Требования к техническому заданию | Описание назначения, функциональности и требований к приложению |
| ГОСТ 19.701-90 | Документация и схемы | Условные обозначения и правила выполнения схем | Подготовка блок-схемы алгоритма оформления заказа |

Примечание: наличие документа в таблице означает использование его положений как методической основы. Полное нормативное соответствие проекта не подтверждалось.

## 3. Совместное применение стандартов

Стандарты не заменяют друг друга, а охватывают разные стороны разработки.

ISO/IEC/IEEE 12207:2026 определяет общую организацию процессов жизненного цикла.

ISO/IEC 25010:2023 помогает определить характеристики качества, которые необходимо учитывать при разработке и оценке программы.

IEEE 1012-2024 задаёт подходы к проверке соответствия результатов разработки требованиям.

ГОСТ 19.201-78 используется как ориентир при подготовке технического задания, а ГОСТ 19.701-90 — при оформлении схем алгоритмов.

Таким образом, процесс разработки, характеристики качества, проверка программы и её документация рассматриваются совместно.

## 4. Применение стандартов в исходном коде

### 4.1. Разделение ответственности

В Program.cs зарегистрирован сервис обработки заказов:

```csharp
builder.Services.AddSingleton<OrderService>();
```

При создании заказа HTTP-обработчик передаёт выполнение сервису:

```csharp
app.MapPost("/api/v1/orders",
    (CreateOrderRequest request, OrderService service) =>
        service.CreateOrder(request));
```

Такое разделение способствует сопровождаемости приложения, что связано с моделью качества ISO/IEC 25010.

### 4.2. Проверка входных данных

В OrderService.cs присутствует проверка пустого заказа:

```csharp
if (request.Items is null || request.Items.Count == 0)
    return Results.BadRequest(new {
        error = "Заказ должен содержать позиции."
    });
```

Также проверяются положительное количество и доступность блюда.

Это обеспечивает часть требований к функциональной корректности.

### 4.3. Обработка ошибок

При обращении к отсутствующему заказу сервер возвращает HTTP 404.

Данное поведение проверяется интеграционным тестом:

```csharp
var response = await client.GetAsync(
    "/api/v2/orders/9999");

Assert.Equal(
    HttpStatusCode.NotFound,
    response.StatusCode);
```

Такая проверка является практическим примером верификации функциональности в контексте IEEE 1012.

## 5. Применение правил оформления C#

Для исходного кода использованы следующие соглашения:

- PascalCase для имён классов и методов;
- camelCase для локальных переменных и параметров;
- понятные имена методов, отражающие выполняемые действия;
- разделение конфигурации API и бизнес-логики;
- использование типизированных записей record для моделей данных.

Примеры: OrderService, CreateOrder, GetOrdersV2, MenuItem.

Соглашения C# являются рекомендациями по стилю программирования, а не самостоятельным доказательством соответствия ГОСТ или ISO.

## 8. Ограничения текущей реализации

Аудит выявил следующие ограничения:

- данные хранятся в оперативной памяти;

- нет авторизации и разграничения прав;
