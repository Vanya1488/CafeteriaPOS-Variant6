## 5. Анализ Program.cs

В исходной версии Program.cs содержал не только объявление HTTP-маршрутов, но и непосредственную обработку заказов.

После рефакторинга обработчики используют внедрение OrderService через механизм dependency injection:

```csharp
builder.Services.AddSingleton<OrderService>();

app.MapPost("/api/v1/orders",
    (CreateOrderRequest request, OrderService service) =>
        service.CreateOrder(request));
```

Это улучшает читаемость и позволяет тестировать логику HTTP API.

## 6. Анализ OrderService.cs

### Валидация заказа

```csharp
if (request.Items is null || request.Items.Count == 0)
    return Results.BadRequest(new {
        error = "Заказ должен содержать позиции."
    });
```

Для каждой позиции проверяется положительное количество и наличие блюда в меню. Цена берётся из серверного каталога, а не из запроса клиента.

### Синхронизация

```csharp
lock (_sync)
{
    order = new Order(
        _orders.Count + 1,
        DateTime.UtcNow,
        lines,
        total,
        "Accepted");
    _orders.Add(order);
}
```

Использование lock предотвращает одновременное изменение списка заказов несколькими потоками. Однако для промышленной системы рекомендуется база данных и транзакционное создание заказов.

## 7. Выявленные недостатки

1. Заказы сохраняются только в оперативной памяти.
2. В приложении отсутствуют аутентификация и разграничение доступа к маршрутам.
3. Swagger включён без ограничения по среде выполнения.
4. Контракты запросов и модели расположены в Program.cs; их можно выделить в отдельные файлы.
5. Нет постоянного хранилища и централизованного журналирования бизнес-событий.
6. Создание заказа проверяет количество, но не устанавливает разумный верхний предел.

Эти недостатки не означают, что учебный прототип неработоспособен: они определяют направления дальнейшего развития.
